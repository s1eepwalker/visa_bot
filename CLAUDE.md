# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Назначение

Бот мониторит свободные слоты на собеседование для визы США в посольстве Астаны (`ais.usvisa-info.com/ru-kz/niv`) и шлёт уведомления в Telegram.

## Команды

```bash
pip install -r requirements.txt   # установка зависимостей
python monitor.py                 # основной запуск (бесконечный цикл)
python update_cookies.py          # ручное обновление cookies.json из строки браузера
pip install pytest && python -m pytest tests   # тесты
```

Тесты — `tests/test_monitor.py` (pytest). В сеть они не ходят: сайт подменяется мини-сайтом на `httpx.MockTransport` с урезанными копиями живых страниц, а `tests/conftest.py` до импорта `monitor` задаёт тестовые переменные окружения (боевой `.env` их не перебивает) и уводит `monitor.log`/`cookies.json`/`booked.json` во временный каталог. Линтеров нет. Логи пишутся в `monitor.log`.

## Конфигурация

Переменные окружения читаются из `.env` (см. `monitor.py:22-28`):
- `TELEGRAM_TOKEN`, `TELEGRAM_CHAT_ID` — обязательные для уведомлений
- `SCHEDULE_ID` — ID записи (из URL `/schedule/<ID>/appointment`), обязателен
- Интервалы проверок задаются **в коде**, а не в `.env`: `INTERVAL_SCHEDULE` и `NIGHT_INTERVAL` в начале `monitor.py`. Число — интервал **на канал**; шаг цикла = интервал / число каналов (снизу зажат `MIN_STEP_SECONDS`). Текущие значения по времени Астаны: утро 08:00-11:00 → 30-35с, день 11:00-12:00 → 45-48с, вечер 12:00-20:00 → 115-150с, ночь 20:00-08:00 → 175-185с. На трёх каналах это даёт шаг 10-12 / 15-16 / 38-50 / ~60с, то есть ~2600 проверок в сутки. Вечер и ночь разрежены 08.09.2026 после блокировки IP VPS: было 65-90 и 90-100 при ~4600 проверках в сутки. Переменная `CHECK_INTERVAL` из `.env` больше не читается. С 11.09.2026 по субботам и воскресеньям утреннего окна нет: `WEEKEND_INTERVAL_SCHEDULE` растягивает дневной темп 45-48с на 08:00-12:00, вечер и ночь как в будни
- `MAX_DATE` — фильтр верхней границы дат (YYYY-MM-DD)
- `EMAIL`, `PASSWORD` — для автологина при истёкшей сессии
- `AUTOBOOK_ENABLED` — `true`/`false`, включает проверку диапазонов автобронирования
- `AUTOBOOK_RANGES` — список `from:to`, разделённых запятыми. `from`/`to` — `YYYY-MM-DD` или относительный токен `today`/`today+N`/`today-N`. Пример: `today+2:2026-08-04,2026-09-03:2026-09-10,2026-09-28:2026-12-31`
- `AUTOBOOK_DRY_RUN` — `true` (по умолчанию) шлёт только Telegram-алерт `AUTOBOOK CANDIDATE` без реального POST. `false` — реальная бронь: `do_real_booking()` GET-ит форму с `BOOKING_URL`, парсит скрытые поля + CSRF, постит с заполненными `appointments[consulate_appointment][date|time|facility_id]`. Успех = 302 на следующий шаг (страховка/подтверждение), неудача = 200 с перерисованной формой. После успеха пишется `booked.json` — с 11.09.2026 это только журнал последней брони, автобронь он больше не выключает. Защита от повторной брони теперь на стороне сайта, см. раздел «Перенос записи»
- `TRANSIENT_RETRIES` — сколько раз повторить запрос дней при 5xx/сетевом сбое перед пропуском итерации (по умолчанию 3, паузы 2/4/7 с + джиттер). Ретраи считаются отдельно от автологина, чтобы истёкшая сессия не съедала бюджет попыток. Ошибки установки соединения (`ConnectError`/`ConnectTimeout`/`ProxyError`/SOCKS `ProtocolError`) при нескольких каналах и `PIN_TARGET_IP=true` не ретраятся — см. «Выходные каналы»
- `FORM_CACHE_TTL` — сколько секунд держать прогретую форму брони (по умолчанию 600)
- `TIMES_RETRIES` / `TIMES_RETRY_WAIT` — сколько раз переспросить `times.json`, если он вернул пустой список времён на дату, которую `days.json` уже показывает (по умолчанию 2 повтора через 3 с). В уведомлениях времена запрашиваются с `retries=0` — там это справочная информация
- `WORKER_PROXIES` — список выходных каналов через запятую, сейчас `zeus=socks5://127.0.0.1:1081,hessen=socks5://127.0.0.1:1082,frank=socks5://127.0.0.1:1083`. Префикс `имя=` необязателен (`parse_worker()`): им подписаны канал в логе (`проверяю (zeus)`, `[zeus] адрес …`) и строка в суточной сводке; без префикса меткой служит сам URL, так было до 11.09.2026. `direct` (запрос с самого VPS) поддерживается, но выключен — см. раздел про выходные каналы. Проверки идут по кругу: каждый канал сохраняет прежний ритм (~интервал расписания), а суммарная частота растёт кратно числу каналов. При одном канале поведение прежнее
- `PIN_TARGET_IP` — `true` (по умолчанию) включает `PinnedHostTransport`: свой пул A-записей сайта вместо штатного резолва. Сопутствующие ручки — `DNS_REFRESH` (300с, как часто перечитывать записи), `IP_QUARANTINE` (180с, карантин отказавшего адреса), `IP_ATTEMPTS` (3, сколько адресов пробовать за запрос). `false` возвращает прежнее поведение
- `MIN_STEP_SECONDS` — нижняя граница шага цикла, чтобы деление интервала на число каналов не ушло в агрессивный опрос (по умолчанию 10)
- `CHANNEL_REPORT_HOUR` — час Астаны, в который раз в сутки уходит сводка по каналам (по умолчанию 8). Сводка — `ChannelStats`: по каждому каналу доля успешных проверок, число провалов и карантинов адресов с прошлой сводки или с запуска; после отправки счётчики обнуляются. Если бот запущен после этого часа, первая сводка придёт на следующее утро
- `REPORT_EVERY` — раз во сколько проверок слать плановую сводку (полный список дат) в Telegram, по умолчанию 500. Было 100, но с ротацией по каналам проверок стало кратно больше и сводки шли слишком часто
- `AUTOBOOK_MIN_LEAD_DAYS` — минимальный запас в днях между сегодня и датой собеседования (по умолчанию 2). Применяется поверх `AUTOBOOK_RANGES`: дата ближе `today+N` кандидатом не становится и вычищается из `autobook_pending`, потому что на такое окно физически не успеть доехать. Нужен потому, что границы диапазонов абсолютные — как только сегодняшнее число войдёт внутрь диапазона (например `2026-09-25…2027-06-30` с 25 сентября), без этого фильтра бот забронировал бы и завтрашний день. «Сегодня» считается по времени Астаны (`ASTANA_TZ`), а не по локальному времени VPS
- `RESCHEDULE_RESERVE` — сколько переносов из лимита сайта бот оставляет нетронутыми (по умолчанию 2). Бот переносит запись, только пока счётчик сайта строго больше резерва: при лимите 3 и резерве 2 это ровно один автоперенос, два остаются на ручные. Подробности — «Перенос записи»

## Выходные каналы (SOCKS)

Окна разбирают быстрее, чем интервал опроса с одного адреса, а частить с одного IP рискованно (429/бан). Поэтому запросы чередуются по трём внешним адресам: `zeus` `37.139.31.183` (порт 1081, ключ `id_rsa-VSCODE`), `hessen` `89.125.68.140` (порт 1082, ключ `andrey`) и `frank` `68.183.64.84` (порт 1083, ключ `andrey`, DigitalOcean fra1). Туннели — обычные `ssh -N -D`, оформлены как systemd-юниты `visa-socks-zeus.service`, `visa-socks-hessen.service` и `visa-socks-frank.service` (`Restart=always`, `enabled`). Требуется `httpx[socks]` (пакет `socksio`).

Канал `direct` (сам VPS `176.126.164.56`) **убран из `WORKER_PROXIES` 08.09.2026**: сайт закрылся от адреса VPS на уровне TCP. Деградация началась 03.09 (~50% отказов `All connection attempts failed`), 07.09 переросла в сброс соединения на путях `/schedule/<ID>/*` со всех выходов, а к утру 08.09 с VPS перестали отвечать все три адреса сайта, тогда как с `hessen` и `frank` отвечали все три.

**Попытка вернуть `direct` 09.09.2026 провалилась, блок держится.** Ручные пробы в 07:05-07:12 показали полностью здоровый канал: TCP на два адреса из трёх в 6 пробах подряд, публичная страница 200 за ~1.35 с, `/schedule/<ID>/*` отвечает приложением. Но как только `direct` вернули в ротацию и с адреса VPS пошёл регулярный опрос, за первые полчаса он дал **1 успех из 10** при 108 карантинах (`ConnectError`, ровно по 36 на каждый из трёх адресов), а прямая проверка TCP в 07:51 отказала на всех трёх адресах в 6 пробах из 6. Конфиг откачен, бот снова на трёх SOCKS-каналах.

Отсюда правило: **разовая проба ничего не доказывает**. Блок то ли снимается на короткие окна, то ли взводится заново от самого трафика с адреса, поэтому проверять `direct` нужно не одним `curl`, а хотя бы получасом реальной ротации, и смотреть на долю успеха по каналу, а не на факт «ответило». Сама проверка: `timeout 5 bash -c 'cat < /dev/null > /dev/tcp/18.254.13.15/443'` с VPS и с любого выходного хоста — разный результат означает, что блок держится. Без браузерного `User-Agent` сайт отдаёт `403` с любого адреса, это WAF на голый curl, а не блокировка.

Отдельно про `zeus`: 09.09.2026 он держит заметно худшую форму, чем соседи — за ночь 08→09.09 57.7% успешных ответов против 87.2% у `hessen` и 82.5% у `frank`, 838 карантинов адресов против 82 и 281, при нормальной медиане ответа 1.22 с. Все карантины — `ProtocolError`, равномерно размазанные по всем трём адресам сайта, то есть это не лежачий узел, а сбросы со стороны сайта; всплески идут пачками ровно по 12 строк (3 адреса × 4 попытки = полный провал итерации) на каждом заходе канала в ротацию. Это тот же почерк, с которого начиналась деградация `direct`. Канал оставлен в работе только потому, что заменить его пока нечем: 57.7% всё равно кратно лучше, чем 10% у заблокированного `direct`. Нужен четвёртый выходной хост.

Статистика по логу на 11.09.2026 (доля проверок, получивших список дат):

| канал | 08.09 | 09.09 | 10.09 | 11.09 |
|---|---|---|---|---|
| `zeus` | 91% | 82% | 92% | 91% |
| `frank` | 98% | 96.5% | 98% | 99.8% |
| `hessen` | 99.5% | 99% | 99.9% | 100% |

HTTP 429 за всё время — ни одного. `zeus` провалы от частоты опроса не зависят: утром (08-11, самый частый опрос) 3-16%, ночью (00, 02, 05, 22, 23 ч) 19-28%. В 23:00 по Астане хуже всем трём каналам. TCP-проба 11.09: с VPS не открывается ни один из трёх адресов, с `zeus` — только `18.254.10.38`, с `frank` — два, кроме `18.254.13.15`, с `hessen` — все три.

Провальная проверка раньше занимала ~19 с — почти всё паузы ретраев. Но ошибка соединения доходит до `fetch_available_days()` уже после того, как транспорт перебрал до `IP_ATTEMPTS` адресов через этот канал. Повтор через тот же канал за 09-11.09 спас проверку лишь 6 раз из 245 у `zeus`, 1 из 36 у `frank` и 0 из 5 у `hessen`, а на `zeus` съедал ~29 минут цикла в сутки. Поэтому с 11.09.2026 при нескольких каналах такая проверка сразу засчитывается провалом, и ход переходит к следующему каналу; провал занимает ~0.6 с. `ReadTimeout` и 5xx ретраятся по-прежнему: там повтор почти всегда проходит. С одним каналом ретраи на ошибках соединения остаются.

При старте запись и счётчик переносов читаются через первый канал из `WORKER_PROXIES`. Если он лежит, стартовое сообщение скажет «текущая запись: нет или не прочиталась», и состояние доберётся на первом же прогреве через живой канал.

Задержка до сайта прямо с хоста-выхода: `frank` 0.73 с и `hessen` 0.79 с — самые быстрые, `zeus` 1.56 с, `direct` 1.62 с (замеры 2026-08-28 и 2026-08-30); при перезамере 09.09 `direct` дал 1.35 с против 1.40 с у `hessen` через SOCKS — но в реальной ротации канал сразу же слёг, см. выше. Через SOCKS с VPS все каналы дают ~1.4-1.5 с (добавляется хоп VPS → выход). Пробовали также `radmin0` `93.91.171.46` — канал снят, юнит удалён.

Проверено 2026-08-28 (и подтверждено для `frank` 2026-08-30): сайт отдаёт 200 со всех адресов, **сессия к IP не привязана** — одни и те же куки работают с любого канала, поэтому логин и `cookies.json` общие, отдельные сессии на канал не нужны. Параллельные сессии одного аккаунта друг друга не выбивают (проверено вторым логином при живой первой), так что при необходимости схему можно расширить. `prohost` как выход недоступен: с VPS его ключи не подходят. Автологин происходит строго раз в час (истечение сессии по времени), ротация по адресам на это не влияет — проверено по логу за 2026-08-28.

Ротация видна в логе — `[#N] HH:MM:SS — проверяю (канал)...` и строка шага с пометкой `на канал раз в ~Nс, каналов M`.

Добавление нового канала: скопировать юнит `visa-socks-<имя>.service` (сменить порт и `andrey@<ip>`), `systemctl enable --now`, дописать `<имя>=socks5://127.0.0.1:<порт>` в `WORKER_PROXIES` в `.env`, `sudo systemctl restart visa-bot`.

## Состав формы бронирования

Проверено на живой странице 2026-08-28. Форма на странице одна — `#appointment-form`, action `…/schedule/<ID>/appointment`. Скрытые поля: `authenticity_token`, `confirmed_limit_message=1`, `use_consulate_appointment_capacity=true`; кнопка `commit=Записаться`. Поля записи — **только** `appointments[consulate_appointment][date|time|facility_id]`; блока `appointments[asc_appointment][...]` в форме нет. `facility_id`: `134` = Астана, `135` = Алматы. Поле `visa_type` в HTML относится к переключателю IV/NIV в шапке сайта, лежит вне формы и не отправляется.

Первая реальная бронь — 11.09.2026: бот сам взял `2027-10-14 09:30` (окно автоброни временно расширили до `2027-10-31` ради проверки). Цепочка GET формы → POST заняла ~1.5 с, POST вернул `302` на `/appointment/instructions`, запись подтвердилась в аккаунте. Критерий успеха «302 не на форму» проверен на живом сайте.

## Перенос записи

Когда запись уже есть, `/appointment` отдаёт не форму, а цепочку из трёх страниц (снято 11.09.2026):
1. **Scheduling Limit Warning** — «Максимальное количество разрешенных отмен/переносов собеседования на этом сервисе: 3. У вас осталось N попыток». На лимите собеседование **блокируется навсегда**, перенести его не сможет ни заявитель, ни поддержка. Дальше GET-форма с галочкой `confirmed_limit_message=1` («Я понимаю»).
2. **Выбор заявителей** — GET-форма с чекбоксами `applicants[]` (в группе 4 человека) и `confirmed_limit_message=1`.
3. **Форма переноса** — тот же `#appointment-form` с теми же полями, что и при первой брони, только кнопка `commit=Перезаписаться` вместо `Записаться`.

Сами GET-страницы попытку не тратят: после нескольких проходов по цепочке счётчик остался 3. Шаг 3 открывается сразу, одним GET со всеми параметрами.

`fetch_booking_form()` проходит цепочку сама: разбирает страницу как форму брони, а если это промежуточная GET-форма (`parse_gate_form()`), идёт по ней со всеми галочками, то есть переносит всю группу целиком. По дороге читает счётчик (`parse_limit_remaining()`); если промежуточная страница была, а счётчик не прочитался, форму не отдаёт. Кеш прогретой формы хранит и счётчик.

Защита перед POST — `reschedule_refusal()` в `do_real_booking()`; для кешированной формы действует так же. Если записи нет (`remaining=None`), это первая бронь и ограничений нет. Иначе POST уходит, только если выполнены все три условия:
- переносов по счётчику больше `RESCHEDULE_RESERVE`;
- известна текущая запись. Бот читает её с `/account` → страница группы → `p.consular-appt` («14 октябрь, 2027, 09:30», `parse_current_appointment()`); если дата неизвестна, перечитывает её прямо перед POST;
- новая дата строго раньше текущей.

В главном цикле кандидаты дополнительно фильтруются `before_appointment()`. Раз в `FORM_CACHE_TTL` вместе с прогревом формы перечитываются запись и счётчик; если попытки ушли, бот ли их потратил или человек вручную, автобронь выключается с Telegram-сообщением. После успешного переноса бот сверяет новую дату с аккаунтом и шлёт «перенос A → B, подтверждено на сайте, переносов осталось N».

При `AUTOBOOK_ENABLED=true` и `AUTOBOOK_DRY_RUN=false` главный цикл раз в `FORM_CACHE_TTL` секунд вызывает `warm_booking_form()`: страница брони скачивается заранее, разобранная форма лежит в `_form_cache`, и при находке слота POST уходит без промежуточного GET. Кеш сбрасывается при автологине (`invalidate_form_cache()`) и при смене cookie-подписи; если POST по кешу не прошёл, `do_real_booking()` делает один повтор со свежей формой.

## Архитектура

Один файл `monitor.py` — асинхронный цикл на `httpx.AsyncClient` + `python-telegram-bot`.

Поток данных:
1. `load_cookies()` читает `cookies.json`. При отсутствии — `do_login()` парсит CSRF-токен из HTML страницы `/users/sign_in`, постит форму, собирает куки и сохраняет.
2. Каждый цикл `fetch_available_days()` дёргает `…/appointment/days/134.json`. На `401`/`302` автоматически вызывает `do_login()` и повторяет запрос (не более одного релогина за вызов — иначе итерация пропускается, чтобы не зациклиться). На `5xx` и сетевых сбоях (`ReadTimeout`, обрыв соединения) делает до `TRANSIENT_RETRIES` повторов. Ошибка установки соединения при нескольких каналах сразу возвращает провал: ход следующему каналу; бюджет ретраев общий для 5xx и таймаутов, но не расходуется релогином. На `429` — Telegram-алерт + экспоненциальный backoff (`note_rate_limit()`: 300с, далее удвоение до потолка 3600с), который главный цикл отрабатывает вместо обычного интервала; первый успешный ответ сбрасывает счётчик (`clear_rate_limit()`) и шлёт сообщение о восстановлении.
3. Сравнение `set(available) - last_known_dates` — уведомление в Telegram только о **новых** датах (чтобы не спамить).
4. Для первых 3 новых дат подгружаются конкретные слоты через `fetch_times_for_date()` (`…/times/134.json?date=…`).
5. Автобронь работает независимо от уведомлений — блок вынесен из-под `if new_dates`. Кандидаты = новые даты, попавшие в `AUTOBOOK_RANGES`, **плюс** отложенные из `autobook_pending`: даты, которые в календаре есть, но `times.json` на них вернул пусто. Такая дата иначе была бы потеряна навсегда — она попадает в `last_known_dates` и «новой» больше не станет, хотя ёмкость может вернуться после чужой отмены (ровно это случилось 16.06.2026 с `2027-02-10`). Даты, выпавшие из календаря, из `autobook_pending` вычищаются. Кандидаты не позже текущей записи отбрасываются (`before_appointment()`). Дальше — `try_autobook()`: в dry-run только Telegram-алерт, в live `do_real_booking()` делает POST, при существующей записи это перенос. На успех пишется `booked.json` (журнал). Продолжать ли автобронь, решает счётчик переносов сайта — см. «Перенос записи».
6. Полный список дат **без фильтра `MAX_DATE`** уходит в Telegram, когда общее число окон выросло относительно прошлой проверки (`last_all_count`), а также раз в `REPORT_EVERY` итераций (по умолчанию 500) как heartbeat. Отдельного HTTP-запроса для этого нет: `MAX_DATE` применяется локально, поэтому цикл делает один запрос с `max_date=""` и фильтрует список в памяти. Сборка и отправка — `report_all_dates()`: сами даты пишутся и в лог, а строка начинается с «Отправлен» или «НЕ доставлен» по фактическому результату.

`send_telegram()` при сетевом сбое повторяет отправку до трёх раз с паузами `TELEGRAM_RETRY_PAUSES` (2 и 5 с); `BadRequest` не повторяется. Без повторов с апреля 2026 пропало 312 сообщений. Все пропажи — `Timed out`: с VPS запрос обычно идёт ~0.5 с, но изредка висит дольше 5 с (таймаут PTB). 11.09.2026 так потерялось «окон стало больше: 0 → 14», первая весть об октябрьских датах 2027 года, а в логе оно значилось отправленным. После таймаута Telegram иногда всё же принимает сообщение, так что повтор может дать дубль.

Эндпоинт `134` в URL — это facility ID посольства Астаны, зашит в константах `DAYS_URL`/`TIMES_URL` (`monitor.py:32-34`).

`PinnedHostTransport` (`monitor.py`) подменяет адрес подключения к `ais.usvisa-info.com`. Сайт живёт на трёх EC2 в `us-gov-east-1` без балансировщика, round-robin в DNS, и узлы флапают: штатный резолв берёт адрес наугад и мёртвый не запоминает, а SOCKS резолвит имя на выходном хосте, где `ssh -D` перебора не делает вовсе. Транспорт держит свой пул A-записей, уводит отказавший адрес в карантин и липнет к последнему удачному. `Host` ставит httpx при сборке запроса, SNI уходит через `extensions["sni_hostname"]`, а `request.url` восстанавливается в `finally` — иначе cookie jar положил бы куки на IP вместо домена. Повтор делается **только** на `ConnectError`/`ConnectTimeout`, до отправки тела, чтобы POST брони не мог переиграться.

`build_headers()` отделяет специальный ключ `_csrf_token` от остальных кук: он уходит в заголовок `X-CSRF-Token`, а не в `Cookie`. Это важно при ручном редактировании `cookies.json`.

`check.py` — одноразовый отладочный скрипт для проверки парсинга CSRF, не часть рантайма.
