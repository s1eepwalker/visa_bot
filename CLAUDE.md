# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Назначение

Бот мониторит свободные слоты на собеседование для визы США в посольстве Астаны (`ais.usvisa-info.com/ru-kz/niv`) и шлёт уведомления в Telegram.

## Команды

```bash
pip install -r requirements.txt   # установка зависимостей
python monitor.py                 # основной запуск (бесконечный цикл)
python update_cookies.py          # ручное обновление cookies.json из строки браузера
```

Тестов нет. Линтеров нет. Логи пишутся в `monitor.log`.

## Конфигурация

Переменные окружения читаются из `.env` (см. `monitor.py:22-28`):
- `TELEGRAM_TOKEN`, `TELEGRAM_CHAT_ID` — обязательные для уведомлений
- `SCHEDULE_ID` — ID записи (из URL `/schedule/<ID>/appointment`), обязателен
- `CHECK_INTERVAL` — секунды между проверками (по умолчанию 90; **не ставить меньше 60** — риск 429/бана)
- `MAX_DATE` — фильтр верхней границы дат (YYYY-MM-DD)
- `EMAIL`, `PASSWORD` — для автологина при истёкшей сессии
- `AUTOBOOK_ENABLED` — `true`/`false`, включает проверку диапазонов автобронирования
- `AUTOBOOK_RANGES` — список `from:to`, разделённых запятыми. `from`/`to` — `YYYY-MM-DD` или относительный токен `today`/`today+N`/`today-N`. Пример: `today+2:2026-08-04,2026-09-03:2026-09-10,2026-09-28:2026-12-31`
- `AUTOBOOK_DRY_RUN` — `true` (по умолчанию) шлёт только Telegram-алерт `AUTOBOOK CANDIDATE` без реального POST. `false` — реальная бронь: `do_real_booking()` GET-ит форму с `BOOKING_URL`, парсит скрытые поля + CSRF, постит с заполненными `appointments[consulate_appointment][date|time|facility_id]`. Успех = 302 на следующий шаг (страховка/подтверждение), неудача = 200 с перерисованной формой. После успеха пишется `booked.json` и autobook отключается до удаления файла (защита от двойной брони)
- `TRANSIENT_RETRIES` — сколько раз повторить запрос дней при 5xx/сетевом сбое перед пропуском итерации (по умолчанию 3, паузы 2/4/7 с + джиттер). Ретраи считаются отдельно от автологина, чтобы истёкшая сессия не съедала бюджет попыток
- `FORM_CACHE_TTL` — сколько секунд держать прогретую форму брони (по умолчанию 600)
- `TIMES_RETRIES` / `TIMES_RETRY_WAIT` — сколько раз переспросить `times.json`, если он вернул пустой список времён на дату, которую `days.json` уже показывает (по умолчанию 2 повтора через 3 с). В уведомлениях времена запрашиваются с `retries=0` — там это справочная информация
- `WORKER_PROXIES` — список выходных каналов через запятую, например `direct,socks5://127.0.0.1:1081,socks5://127.0.0.1:1082`. `direct` — запрос с самого VPS, остальные — SOCKS5-прокси. Проверки идут по кругу: каждый канал сохраняет прежний ритм (~интервал расписания), а суммарная частота растёт кратно числу каналов. При одном канале поведение прежнее
- `MIN_STEP_SECONDS` — нижняя граница шага цикла, чтобы деление интервала на число каналов не ушло в агрессивный опрос (по умолчанию 10)
- `REPORT_EVERY` — раз во сколько проверок слать плановую сводку (полный список дат) в Telegram, по умолчанию 500. Было 100, но с ротацией по четырём каналам проверок стало кратно больше и сводки шли слишком часто
- `AUTOBOOK_MIN_LEAD_DAYS` — минимальный запас в днях между сегодня и датой собеседования (по умолчанию 2). Применяется поверх `AUTOBOOK_RANGES`: дата ближе `today+N` кандидатом не становится и вычищается из `autobook_pending`, потому что на такое окно физически не успеть доехать. Нужен потому, что границы диапазонов абсолютные — как только сегодняшнее число войдёт внутрь диапазона (например `2026-09-25…2027-06-30` с 25 сентября), без этого фильтра бот забронировал бы и завтрашний день. «Сегодня» считается по времени Астаны (`ASTANA_TZ`), а не по локальному времени VPS

## Выходные каналы (SOCKS)

Окна разбирают быстрее, чем интервал опроса с одного адреса, а частить с одного IP рискованно (429/бан). Поэтому запросы чередуются по четырём внешним адресам: сам VPS `176.126.164.56`, `zeus` `37.139.31.183` (порт 1081, ключ `id_rsa-VSCODE`), `hessen` `89.125.68.140` (порт 1082, ключ `andrey`) и `frank` `68.183.64.84` (порт 1083, ключ `andrey`, DigitalOcean fra1). Туннели — обычные `ssh -N -D`, оформлены как systemd-юниты `visa-socks-zeus.service`, `visa-socks-hessen.service` и `visa-socks-frank.service` (`Restart=always`, `enabled`). Требуется `httpx[socks]` (пакет `socksio`).

Задержка до сайта прямо с хоста-выхода: `frank` 0.73 с и `hessen` 0.79 с — самые быстрые, `zeus` 1.56 с, `direct` 1.62 с (замеры 2026-08-28 и 2026-08-30). Через SOCKS с VPS все каналы дают ~1.4-1.5 с (добавляется хоп VPS → выход). Пробовали также `radmin0` `93.91.171.46` — канал снят, юнит удалён.

Проверено 2026-08-28 (и подтверждено для `frank` 2026-08-30): сайт отдаёт 200 со всех адресов, **сессия к IP не привязана** — одни и те же куки работают с любого канала, поэтому логин и `cookies.json` общие, отдельные сессии на канал не нужны. Параллельные сессии одного аккаунта друг друга не выбивают (проверено вторым логином при живой первой), так что при необходимости схему можно расширить. `prohost` как выход недоступен: с VPS его ключи не подходят. Автологин происходит строго раз в час (истечение сессии по времени), ротация по адресам на это не влияет — проверено по логу за 2026-08-28.

Ротация видна в логе — `[#N] HH:MM:SS — проверяю (канал)...` и строка шага с пометкой `на канал раз в ~Nс, каналов M`.

Добавление нового канала: скопировать юнит `visa-socks-<имя>.service` (сменить порт и `andrey@<ip>`), `systemctl enable --now`, дописать `socks5://127.0.0.1:<порт>` в `WORKER_PROXIES` в `.env`, `sudo systemctl restart visa-bot`.

## Состав формы бронирования

Проверено на живой странице 2026-08-28. Форма на странице одна — `#appointment-form`, action `…/schedule/<ID>/appointment`. Скрытые поля: `authenticity_token`, `confirmed_limit_message=1`, `use_consulate_appointment_capacity=true`; кнопка `commit=Записаться`. Поля записи — **только** `appointments[consulate_appointment][date|time|facility_id]`; блока `appointments[asc_appointment][...]` в форме нет. `facility_id`: `134` = Астана, `135` = Алматы. Поле `visa_type` в HTML относится к переключателю IV/NIV в шапке сайта, лежит вне формы и не отправляется.

Реальных попыток брони пока не было ни одной (`booked.json` не создавался), поэтому поведение сервера на POST не проверено — совпадает только структура запроса.

При `AUTOBOOK_ENABLED=true` и `AUTOBOOK_DRY_RUN=false` главный цикл раз в `FORM_CACHE_TTL` секунд вызывает `warm_booking_form()`: страница брони скачивается заранее, разобранная форма лежит в `_form_cache`, и при находке слота POST уходит без промежуточного GET. Кеш сбрасывается при автологине (`invalidate_form_cache()`) и при смене cookie-подписи; если POST по кешу не прошёл, `do_real_booking()` делает один повтор со свежей формой.

## Архитектура

Один файл `monitor.py` — асинхронный цикл на `httpx.AsyncClient` + `python-telegram-bot`.

Поток данных:
1. `load_cookies()` читает `cookies.json`. При отсутствии — `do_login()` парсит CSRF-токен из HTML страницы `/users/sign_in`, постит форму, собирает куки и сохраняет.
2. Каждый цикл `fetch_available_days()` дёргает `…/appointment/days/134.json`. На `401`/`302` автоматически вызывает `do_login()` и повторяет запрос (не более одного релогина за вызов — иначе итерация пропускается, чтобы не зациклиться). На `5xx` и сетевых сбоях (`ReadTimeout`, `ConnectTimeout`, обрыв соединения) делает до `TRANSIENT_RETRIES` повторов; бюджет ретраев общий для 5xx и таймаутов, но не расходуется релогином. На `429` — Telegram-алерт + экспоненциальный backoff (`note_rate_limit()`: 300с, далее удвоение до потолка 3600с), который главный цикл отрабатывает вместо обычного интервала; первый успешный ответ сбрасывает счётчик (`clear_rate_limit()`) и шлёт сообщение о восстановлении.
3. Сравнение `set(available) - last_known_dates` — уведомление в Telegram только о **новых** датах (чтобы не спамить).
4. Для первых 3 новых дат подгружаются конкретные слоты через `fetch_times_for_date()` (`…/times/134.json?date=…`).
5. Автобронь работает независимо от уведомлений — блок вынесен из-под `if new_dates`. Кандидаты = новые даты, попавшие в `AUTOBOOK_RANGES`, **плюс** отложенные из `autobook_pending`: даты, которые в календаре есть, но `times.json` на них вернул пусто. Такая дата иначе была бы потеряна навсегда — она попадает в `last_known_dates` и «новой» больше не станет, хотя ёмкость может вернуться после чужой отмены (ровно это случилось 16.06.2026 с `2027-02-10`). Даты, выпавшие из календаря, из `autobook_pending` вычищаются. Дальше — `try_autobook()`: в dry-run только Telegram-алерт, в live `do_real_booking()` делает POST. На успех создаётся `booked.json`, autobook отключается на всю сессию и при следующих рестартах (пока файл не удалят).
6. Полный список дат **без фильтра `MAX_DATE`** уходит в Telegram, когда общее число окон выросло относительно прошлой проверки (`last_all_count`), а также раз в `REPORT_EVERY` итераций (по умолчанию 500) как heartbeat. Отдельного HTTP-запроса для этого нет: `MAX_DATE` применяется локально, поэтому цикл делает один запрос с `max_date=""` и фильтрует список в памяти.

Эндпоинт `134` в URL — это facility ID посольства Астаны, зашит в константах `DAYS_URL`/`TIMES_URL` (`monitor.py:32-34`).

`build_headers()` отделяет специальный ключ `_csrf_token` от остальных кук: он уходит в заголовок `X-CSRF-Token`, а не в `Cookie`. Это важно при ручном редактировании `cookies.json`.

`check.py` — одноразовый отладочный скрипт для проверки парсинга CSRF, не часть рантайма.
